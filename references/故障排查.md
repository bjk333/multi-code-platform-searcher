## 输出流与编码纪律

- `.ps1` 必须保持 UTF-8 BOM（PS 5.1 对无 BOM 的 UTF-8 中文按 GBK 误读 → 解析/运行失败）。
- `SKILL.md` / `references/*.md` 必须**无 BOM**（DSH frontmatter 解析要求）。编辑工具写回后若被加 BOM，用下述命令剥离：

```powershell
$p = "path\to\file.md"
$t = [System.IO.File]::ReadAllText($p, [System.Text.UTF8Encoding]::new($false))
[System.IO.File]::WriteAllText($p, $t, [System.Text.UTF8Encoding]::new($false))
```

## .env 令牌文件权限（v1.25.0 实测经验）

- `.env` 含密钥，建议锁定为只读，但**必须同时给 SYSTEM 读权限**——DSH 技能进程可能以 SYSTEM 账户运行，
  锁成"仅当前用户可读"会导致 `Load-EnvFile` 读文件抛异常（被 catch 吞掉）、token 静默失效（`-Doctor` 显示
  Present=false，代码证据回退 Blocked）。现象排查：`whoami` 若返回 SYSTEM，即属此场景。
- 正确 ACL（SYSTEM 只读 + 当前用户只读 + 保留继承以便用户编辑）：
  ```powershell
  icacls <env路径> /inheritance:e
  icacls <env路径> /grant:r "SYSTEM:(R)"
  icacls <env路径> /grant:r "<用户域>\<用户>:(R)"
  ```
- 锁定后务必验证：`-Doctor -AsJson` 中 `GITHUB_TOKEN/GITLAB_TOKEN Present=true`，且 `-CodeEvidence` 里
  GitHubCode 进入 `Executed`（而非 Blocked）。

## 已知环境限制

- **Gitee API**：部分沙箱/企业网络防火墙拦截 Gitee（GitHub 白名单放行时 Gitee 不通）——失败自动跳过不阻断，需在可直连 Gitee 的环境复测。
- **Stack Exchange**：匿名配额低（~300 次/天），高频批量建议配 `SE_KEY`。
- **arXiv**：`Stars=0`（基础 API 无引用数），v1.18 起经 Semantic Scholar batch 补全。
- **GitHub code search**：仅默认分支、单文件 <384KB、REST 不支持 `pathname:`（用 `path:`/`filename:`）。
- **Maven Central**：`Stars=0`（solrsearch 无下载量字段）。

## Git 忽略规则与已跟踪文件（M-5b）

`git check-ignore -v <path>` 只能解释**忽略规则候选**，不能证明该路径没有被 Git 跟踪；`git ls-files -i -c --exclude-standard` 才列出「**已经跟踪、但仍匹配忽略规则**」的交集。在 canonical 仓根运行两条命令并保存退出状态：

```powershell
git check-ignore -v tools/bin/rg.exe
git ls-files -i -c --exclude-standard
```

第二条没有输出才可判交集为空；在没有 Git 仓元数据或不能访问仓根的容器里，只能报告静态候选，**不得**声称已完成 Git 交集核查。不要用 `git rm --cached` 去替代核查（修改索引需另行授权）。

## MCPS_PROXY 域名白名单治理（T1-1）

- **需要核查**：`gitlab.com`——本机 2026-09-25 曾因白名单漏此域而直连超时，令牌可用性被误判；在该机必须纳入有效的代理路由或先证明可直连。`gitee.com` 仅在直连失败且代理可用时纳入；`api.github.com` 若直连/本地 hosts 接管可用则不强制入名单。
- **不应盲目加入**：`grep.app` 的 Vercel 安全检查页（长效 429）和 Gitee 搜索接口级风控并非添加白名单就能解决；`Sourcegraph` 403 也不自动等同代理问题。`MCPS_PROXY` 不写分号白名单时为**所有域**走代理。
- **安全自查（只读当前进程）**：桥屏蔽 `.env`，下方**不读取文件、不 dot-source 脚本、不打印代理地址或令牌**；只核对当前进程已有的 `MCPS_PROXY`。若配置仅在 `.env` 中，本命令会显示 `not-in-process`，**不能据此断定 `.env` 未配置**；请有权限的宿主操作者在安全终端自行加载并复核，不通过桥绕过屏蔽。改白名单前仍需核查路由与访问授权。

```powershell
$proxySpec = [string]$env:MCPS_PROXY
if ([string]::IsNullOrWhiteSpace($proxySpec)) {
    [PSCustomObject]@{ Mode = 'not-in-process'; DomainCount = 0; GitLabCovered = $false; GiteeCovered = $false }
} elseif ($proxySpec -notmatch '^socks5://') {
    [PSCustomObject]@{ Mode = 'other'; DomainCount = 0; GitLabCovered = $false; GiteeCovered = $false }
} else {
    $allow = if ($proxySpec.Contains(';')) {
        @($proxySpec.Substring($proxySpec.IndexOf(';') + 1) -split ',' | ForEach-Object { $_.Trim().ToLower() } | Where-Object { $_ })
    } else { @('*') }
    [PSCustomObject]@{ Mode = 'SOCKS5'; DomainCount = $allow.Count
        GitLabCovered = ($allow -contains '*' -or $allow -contains 'gitlab.com')
        GiteeCovered = ($allow -contains '*' -or $allow -contains 'gitee.com') }
}
```

**现状**：Doctor 已接入 T1-2 代理一致性候选逻辑（JSON `doctor.proxyConsistency[]`，文本模式提示）；PS 5.1 / PS 7.6.6 的 12h 离线注入夹具均通过。真实受限网络下的域名路由仍须逐环境实测；`tokens[].Probe=unreachable` 时先按白名单和链路自查，勿把它当令牌撤销。

**v1.53.26 起不必手拼上面的命令**：`-Doctor` 新增 `proxyCoverage`（JSON `doctor.proxyCoverage.rows[]`），逐引擎列出
`Host` / `Route`（实际候选链）/ `Whitelist`（`allowed` | `excluded` | `all` | `n/a`）/ `NoProxy` / `Hijack`。
判读顺序：先看 `Route` = **实际会发生什么**，再看 `Whitelist` = **为什么**（`excluded` = 该域被 `;` 后面的白名单排除，
`MCPS_PROXY` 根本没进候选）。排除项只在"已无其他代理候选、只剩直连"时印红 —— 本机白名单只覆盖 GitHub，
20 个域都是 `excluded`，全红就是噪声。`Hijack` 列只提示不判红：hosts 指到回环时**直连/本地解析必失败**，
但 `socks5h` 由代理解析域名、不受影响。★`Host` 字段**只用于诊断**，选路仍由 `Get-NetworkCandidates` 逐域决定。

## R-2b：[string] 参数默认 null 的判空陷阱

PowerShell 的 `[string]$Body = $null` 在函数入口可能变为 `''`；`$null -ne $Body` 不能用于判断是否有请求体。曾使 TLS 兜底的 GET 意外传 `-B <空文件>`，宿主原始失败证据见 `reports/宿主日志-2026-09-25-182x.md`。现以 `[string]::IsNullOrEmpty($Body)` 为界：GET 不携带体，非空 POST 仍走 `-B`。保留 `tests/run-tests.ps1` 中 GET/POST 双向 12e 断言，以及 Node 中将判据改回旧写法应失败的离线负对照。限定扫描 B 的 `*.ps1`，唯一 `[string]` 参数默认 `$null` 为本处；其余 `$null -eq/-ne` 命中须结合对象或未约束的值逐个核实，不机械替换。

## 网络路由决策表（U-56）—— 一次请求到底走不走代理，谁说了算

**判读口诀**：任何 HTTP 响应（包括 401/403/429/5xx）代表**网络可达**，要按令牌/配额/服务端错误另行分类；仅所有候选均明确 DNS/连接被拒且 GET 复核失败才记 `coverage.ReasonCodes[引擎]=network-unavailable`、`Blocked`、`Verdict=none/partial`。localhost 既可能是活代理也可能是死代理，不按地址形状清理。历史 U-40 的 PS7 原生默认读环境、PS5.1 原生不读的机制仍成立，但 **U-156 的产品选路显式读取两运行时的进程代理**。

## 无 ReasonCode ≠ 无问题（v1.47.1，审计实测）

`coverage.Reasons` / `ReasonCodes` 为空、或只有一句"超时"，**不能**反证网络正常。两条机制：

1. **deadline 自带网络证据（但要看它是哪一种）**：`单引擎超 <dlSec>s 截止，已停止` 这个模板只带秒数，没有 hosts / 选路字段；网络归因由 `Get-ApiRequestRouteContext` 写 —— `network-unavailable`（写完即 `throw`）与 `network-route-unproven`（写完继续发请求）。**v1.47.2 起**探活前先写占位 `network-route-unproven: <host>（探活未完成即被打断）`，所以"探活途中被截止"不再是零证据；**v1.49.1 起**探活一旦确认可达就把这条占位**撤回** —— 于是这条标记的语义被收紧成一句话：**它还在 = 探活确实没有结论**。
   - 看到 `<…>（探活未完成即被打断）` 或 `（未确认的路由：X）` ⇒ 引擎根本没走到发请求/或路由没验成 ⇒ 是**本机网络/路由**问题；
   - 只看到光秃秃的「超 Ns 截止」⇒ 探活要么已确认可达（请求随后挂住），要么压根没跑 ⇒ **不能**归给网络，按产品侧可疑处理。
2. **`Stop()` 停不住同步探活**：探活走 `HttpWebRequest`，`Timeout` 不封顶 DNS / 代理 CONNECT；到点时 `$h.PS.Stop()` 只是不再等结果，探活本身仍占线程 ⇒ 上述"被打断"在慢代理下是常态而非偶发。

**判别动作**（看证据，不看状态码）：

- 先查 `coverage.Reasons.<引擎>` 里有没有 hosts 原始行 / `选路：` / 白名单缺哪个域；没有就**不能**下"远端无数据"的结论。
- 同一域换 `-ProxyMode direct` 或临时 `MCPS_PROXY_FALLBACK=1` 复跑一次：结论变了 ⇒ 是路由问题，不是源里没有内容。
- 要确定性诊断就用 `-Doctor`（它带总预算做逐域探活，归因不依赖 deadline 竞态）。

```bash
python mcps.py -Doctor -AsJson --out C:/tmp/doctor.json
# 然后看 doctor.deadlinePolicy.Resolved[]：{Engine, Seconds, Source, TableSeconds}
```

- `Source=table`：就是表值（HF 默认 8s 属这一类）。
- `Source=cap`：**表值被硬上限夹住了**。v1.47.9 起默认 `EngineHardCapSec=0`（关闭）⇒ 默认**不会出现**这一类；
  只有显式设了 `MCPS_ENGINE_HARD_CAP_SEC` 才会看到（例如设 10，则表里 28/29/26 实际都只等到 10s，
  21 个引擎里 17 个如此，`CappedCount` 直接给数）。要让某个源真的等更久：删掉该环境变量（回到 v1.47.9 默认），
  或用 `MCPS_ENGINE_DEADLINE="Npm=15"`（逐源、且**不被**上限夹；U-243 起包注册表已拆成 Npm / Crates / Maven 三个引擎，名字各自独立）。
- `Source=env`：`MCPS_ENGINE_DEADLINE` 显式覆盖生效中（`EnvOverride` 会回显原串）。
- `Source=off`：该源单源截止被 `Name=0` 关闭（全局时间预算仍生效）。

> 别用"表里写 28 所以它等 28s"推理 —— 先看 `Source`：v1.47.9 起默认成立（cap 关闭），
> 但只要环境里有人设了 `MCPS_ENGINE_HARD_CAP_SEC`，`Source=cap` 就会告诉你实际只等到几秒。

`CappedCount > 0` 时 `deadlinePolicy.Advice` 会直接给出两个受支持旋钮（v1.47.7）。
实测（n=2，`-ResearchSources "vector database"`，见 `reports/实验-截止上限与预算-2026-10-22.md`）：
v1.47.9 默认（cap=0）⇒ **25 条/1 个 deadline/17–20s**；`MCPS_ENGINE_HARD_CAP_SEC=10` ⇒ 18 条/3 个 deadline/15.8s。
默认取覆盖优先；宁可快、接受少 7 条的一方设 `MCPS_ENGINE_HARD_CAP_SEC=10` 即可回退；
`-Auto` 不受影响（多模式走 `EngineHardCapMultiModeSec=25`）。

**时间预算也是"每池各算"**（v1.47.6 起 `doctor.budgetPolicy` 直接给数）：

- `MCPS_TIME_BUDGET_SEC`（默认 120）在 `Invoke-EnginePool` 里被读一次，**每个池各算一份**。
- `-Auto` 顺序跑 repo / code / research 三个池 ⇒ 进程内**最坏 3×预算**（默认 360s），池间缝隙不计。
- `budgetPolicy.SharedAcrossPools=false` 就是当前语义。看到 `-Auto` 跑得比 120s 久，先看这个字段，别怀疑计时。
- 全局 `mcps.py --timeout` 是外层看门狗：它先到点会直接杀进程，此时 JSON 可能来不及落盘。

## 「本地检索没接管」到底为什么（v1.47.8）

`-LocalCodeSearch` 在本地拿不到结果时会降级到远程 code 引擎。告警现在会**照抄引擎给的原因**：

```
[LocalCode] 本地检索未接管（需要存在的 -LocalPath 目录（当前: Z:/no/such/dir））：已降级到远程 code 引擎…
[LocalCode] 本地检索未接管（未找到 rg/ugrep）：已降级到远程 code 引擎…
[LocalCode] 本地检索未接管（检索成功但命中 0 条）：已降级到远程 code 引擎…
```

三种原因指向三种处置：**改路径 / 装 ripgrep / 换关键词**。旧文案一律说「0 命中（或二进制缺失）」，
路径写错的人会被引去查代码内容 —— 这是 v1.47.8 修掉的实际误诊。

## `-ResearchBatch` 的输入错误长什么样（v1.47.8）

| 情况 | 退出码 | 载荷 |
|---|---|---|
| 文件不存在 | 1 | `error=invalid-batch-input`，`message` 写明路径问题 |
| 非 UTF-8 JSON | 1 | 同上，`message=…must be valid UTF-8 JSON.` |
| 形状不对（标量） | 1 | 同上，`message=…expects a JSON array or {"queries":[...]}` |
| 条数不在 1..64 | 1 | 同上 |

信封形状与参数错误一致（`version/error/message/usage/results/warnings`），`warnings` 里带「未执行任何检索」。

## PS 门禁的环境前提：进程级代理（N-16 / U-40）

- **机制**：PS 7（.NET Core）的 `HttpClient` **默认读进程环境变量 `HTTP_PROXY`/`HTTPS_PROXY`**；PS 5.1（.NET Framework）走系统代理、不读它们。宿主 2026-09-26 受控 A/B：同一份 B v1.37.7，PS 7 本地组**带 `HTTP_PROXY` 红 3 次、清空绿 2 次**，唯一变量就是该环境变量（`reports/gates/环境前提-N-16-2026-09-26.md`）。
- **U-40 修法（v1.37.8）**：`-NoProxy` 现在在两运行时都**真正直连** —— Core 用 `Invoke-WebRequest -NoProxy`，Desktop 在调用期间把 `DefaultWebProxy` 置空代理并 `finally` 复原；不改系统设置、不改进程环境变量。`$script:LastRequestProxyMode` 记录实际走的模式（`direct-noproxy-core` / `direct-emptyproxy-desktop` / `default`），12e 会断言它。
- **门禁纪律**：① 手工跑 PS 门前**记录**代理状态（12e 现自动打印 `env-proxy=…`），凡结论依赖环境的门须在**带/不带代理两个环境各留一次原始输出**；② 证据不变式是 **`0 failed` + `rc=0`**，不要迷信 passed 数（`test-citations` 不可达按设计 SKIP）；③ 跨运行时差异必须落到运行时机制解释，不得只写"PS 7 行为不同"。
- **`MCPS_PROXY`（socks5 白名单）与进程级 `HTTP_PROXY` 是两层**：U-156 `auto` 先后探活这两类候选，选到活代理再发真实请求；`-NoProxy` / `-ProxyMode direct` 两层都绕过。`Initialize-Network` **不再清理任何**指向 127.0.0.1 的变量；即使 12e 发现它存在也不能单凭地址判断死活。

## 两侧运行时分工与门禁入口（N-12/N-13）

- **Windows 宿主**：有原生 PS 5.1 与签名验证过的便携 PS 7.6.6。对 B 分别用 `run_project_test(root=bline, entry=tests|tests-local)`、`entry=ps7-tests|ps7-local`；A 由宿主另跑对应门。每次留逐组输出与 rc，不能跨运行时、跨副本替代。
- **Linux B 容器**：可跑 `node tests/run-node-gates.mjs`（v1.37.6 共 23 个测试）；没有自装 pwsh。Linux Node 结果只证实离线 Node 门，不替代宿主 Windows PS 5.1 / PS 7 门；便携 PS 7 通过宿主固定入口调用，不擅自安装或切换桥本机档。
- **宿主 Node**：WorkBuddy 的 `NODE_OPTIONS` shim 曾使 `spawnSync` 报 `EBUSY`；N-11 改异步 `spawn`。R12 最终 36 项产物在 A/B 各自 `node tests/run-node-gates.mjs` 均 23/23、rc=0。`node --test tests` 不是入口；在技能根用 `node tests/run-node-gates.mjs`，或进 `tests/` 再用 `node --test`。
- **宿主 Node 垫片的两条同源症状（2026-10-02 实测，走非垫片 node 即消）**：
  - **`fs.cpSync(src, dst, { recursive: true })` 的 `src` 路径含非 ASCII 就硬崩**：node 进程 `0xC0000409`（STATUS_STACK_BUFFER_OVERRUN），stdout 全丢、无任何错误文本。本项目 canonical 位于 `<workspace>\…`，任何"复制 engines/schema 到临时树"的门（`test-r96-injection-invariants`、`test-r96-live-payload`）在宿主会**整文件红**且看不出原因；最小复现 = 建一个含中文名的 temp 目录放两个文件再 `cpSync`（ASCII 路径 19 个文件 72 KB 也正常，见 `_diag/b9.mjs`）。**修法：跑 Node 门用系统 node**（`& "C:\Program Files\nodejs\node.exe" tests\run-node-gates.mjs`，并把 `NODE_OPTIONS` 清空），不要用 `.workbuddy\binaries\node\…`（带 `node-language-shim.cjs` / `node-brokered-fs-shim.cjs`）。
  - **中文 Windows 控制台码页 cp936 ⇒ PS 子进程的非 ASCII stdout 是 GBK 字节**：门若一律按 UTF-8 解码，`≠`、`一致`、`不在白名单` 这类**标记**会变成 U+FFFD，出现"rc 正确但标记比不中"的假红（实测：`test-r2m-ripgrep-lock` 的 `size=11≠4218880` 与 `OK … sha256 一致` 两条）。`tests/r2-ps-run.mjs` 已改为收 Buffer 解码：UTF-8 出现替换符时回退 GBK 系码页（纯 ASCII 输出行为不变）。主脚本 `-AsJson` 不受影响 —— 它已在 `main:3175` 显式设 `[Console]::OutputEncoding=UTF8`。
- `tests/test-retry.ps1` 是参考副本，不是独立门禁：宿主曾出现内部 `TEST_FAIL` 但进程 rc=0 的**假绿**。应通过 `tests/run-tests.ps1` 的 `[test-retry]` 与总 rc 验收，不能引用单跑参考副本的退出码。
