# 与直接调研的协同工作流 + 端到端范例

> 版本说明：本文件只描述方法与协同边界，**不含版本相关行为**，故标题不挂版本号（文档门 G1 只校验挂了版本号的标题）。行为随版本变化的内容在 `引擎链.md` / `参数速查.md`。

## 为什么需要协同

| 路径 | 强项 | 弱项 |
|---|---|---|
| 直接调研（web_search + read_page） | 叙事层/深读/时效 | 代码级召回/可复现 |
| 本技能 | 结构化召回/JSON 契约/可审计 | 环境依赖/宽概念语义 |

二者互补：**技能只采证据、不代判断**；判断交给阅读原文/源码。

## 三段式协同流程（固化）

1. **定全貌**：直接搜 / web 检索官方文档、标准、博客、论坛，明确概念、接口、约束与方向（web 5+3 路）。
2. **补召回与实证**：用本技能做仓库/代码/论文结构化召回——**先跑 `-Doctor` 校准能力边界**（缺 rg/token 直接告知），再按需：
   - 相似项目：`-Keyword "<概念>" -Platform All`
   - 代码实现证据：`-CodeEvidence`（先看 `coverage`/`warnings`，Blocked/Degraded 时不能把 0 命中当"确实没有"）
   - 论文/包/问答：`-ResearchSources`（0 命中用 `-ExpandQuery` 看 `research` 契约）
3. **下判断**：回读源码/文档原文做最终判断。技能输出是候选，使用者自行核验仓库、分支、适配性。

## r1–r4 三类输出解读（第二轮实跑教训）

### ① 宽概念噪音（r1 教训）
`llm flow monitor console` 这类宽概念句 → 召回被热门通识项目（AutoGPT/ollama 高星 + 命中一个宽词即排前）霸榜。
**应对**：加 `-FocusTerms` 把语义限定词显式化（如 `-FocusTerms session,alert`），或提高 `-MinStars`；看每条 `Score`/`MatchTerms`/`NoiseFlagged` 识别噪音候选。

### ② 检索失败伪装成 0 命中（r2 教训）
无 `rg.exe` + 无 `GITHUB_TOKEN` → 代码证据"0 命中 + success"极易被误读成"确实没有匹配"。
**应对**：先 `-Doctor`；看 `coverage`：`Blocked=[GitHubCode(auth_missing),...]` + `Degraded=[...]` + `warnings[]`——**这些状态下 0 命中不可信**。

### ③ 0 命中 ≠ 不存在（r3 教训）
研究信源对"会话级告警标准协议" 0 命中时，无法区分「确实没有」与「查询词太窄」。
**应对**：加 `-ExpandQuery`；看 `research` 契约：`interpretation=no-match` + `lowConfidenceNegative=true` + `suggestedWiderQueries[]`（恒非空）——**引导 Agent 用 web 二次印证，不轻易下"无此标准"结论**。

### ④ 引擎降级可审计（r4 教训 / v1.23 起）
任何引擎失败/降级进顶层 `warnings[]`：`[Engine] 消息 (from: X -> Y)`。
**应对**：读 `warnings[]` 得知"谁降级了、为什么、从哪到哪"，再决定是否补通道（如换网络让 grep.app 恢复、配 token 解锁 GitHubCode）。

## 端到端范例（本升级计划即范例）

本技能 v1.21.0–v1.24.0 的全部升级项均按上述三段式产生：
1. 第一轮实跑（r1–r4）暴露 5 类问题（宽概念噪音/代码证据静默失效/研究源 0 命中/环境依赖/结构评测缺失）；
2. 全网调研（GitHub API 限流、grep.app MCP、Sourcegraph Code Finder、查询理解、PowerShell 可观测性、Agent Skills 评测、OTel GenAI 约定）把每个问题固化成带证据/方案/验收的升级项；
3. 逐版本实施 + 端到端复测闭环（每版 `reports/v1xx-*.md` 记录验收证据）。

**参考**：`multi-code-platform-searcher升级计划_2026-08-22.md`（P0–P2 七项）、`reports/` 下各版本验收报告、`tests/` 与 `evals/` 回归。

## 标杆发现：从官方定义到可复核的实现候选（U-117）

**场景**：为“分布式追踪系统性能基准”找可对照的开源实现。这里的“标杆”是待验证候选，不是按 Star 数或模型输出直接认定的冠军；下面是**用法**，不是本页已经实跑出的命中清单。

1. **先定义比较口径**：直接读标准维护方/项目发布方的现行规范、官方基准说明，记版本、日期、测量项和运行环境。纯“概念/标准是什么”的问题到此应以官方原文为主，不让包/论文/问答搜索代答。
2. **校准通道**：`python mcps.py -Doctor -AsJson --out C:/tmp/mcps/doctor.json`；确认所需引擎可用、凭据/工具状态，而不是把 `results=[]` 当成“没有标杆”。
3. **找候选项目**：`python mcps.py -Keyword "distributed tracing benchmark" -Platform All -MinStars 0 -Limit 5 -AsJson --out C:/tmp/mcps/bench-repos.json`。查看 `coverage.Requested/Executed/Blocked/Degraded/ReasonCodes`、`results[].Url`、项目维护状态和许可证，保留来源链接。
4. **找可复现的实现证据**：`python mcps.py -CodeEvidence -Keyword "tracing benchmark harness" -AsJson --out C:/tmp/mcps/bench-code.json`；按文件路径和具体源码验证是否含基准脚本、固定输入与复现说明。`Verdict=full` 只说明引擎执行过，不保证有合格实现。
5. **补论文/包/问答**：`python mcps.py -ResearchSources -Keyword "distributed tracing benchmark" -Limit 5 -AsJson --out C:/tmp/mcps/bench-research.json`；研究源约为包、论文、问答/社区，逐条回读原文；它不直接覆盖官方标准。
6. **形成标杆候选表**：逐条记录“官方比较口径 → 项目链接/版本 → 代码文件与运行命令 → 许可/测试与数据集 → 各源 coverage/失败原因 → 原文复核结论”。有 `auth_missing`、`tool_missing`、网络降级或低置信度 0 命中时标**未覆盖**，不能写成“无此标杆”。
