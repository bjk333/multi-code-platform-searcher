## v1.69.0（2026-10-27 结构批 B3-16）：**两条"判词"级别的门改跑产品** —— verdict 顺序 / 进程 rc / AND 注解。

  这一批换的不是"实现细节"，而是**调用方拿去做决定的那两个词**：`coverage.Verdict` 与进程 rc。
  两者此前都只有静态门守着（grep 源码里的分支顺序），而它们的错法**都不会报错，只会骗人**。

  ### U-120：`none` 必须先于 `partial` 判定

  原门的断言是"`return 'none'` 出现在 `return 'partial'` 之前"。顺序确实重要 —— 两句一换位，
  行为就变成"一个源都没查成，却告诉你部分成功"。现在三条臂各跑一次 CLI：

  | 臂 | 场景 | 断言 |
  |---|---|---|
  | A | 只剩两个"没令牌就不发请求"的引擎 | `Executed=[]` + `Blocked=2` ⇒ **`none`**，进程 **rc=3** |
  | B | Sourcegraph 跑通 + 两个阻塞 | `partial`，进程 **rc=0** |
  | C | 全部禁用（`Requested=[]`）| **`no-engines`**，进程 **rc=4** |

  B 那一行是本批新增的契约：**rc 只回答"这次有没有结论"**。把 partial 也算失败的话，多源聚合下
  几乎每轮都有源被挡，rc 就成了常量噪声，反而看不见真失败。

  ### U-175：AND 注解与"不自动放宽"

  原门 grep `AND 语义` / `$tc -ge 3` / `不自动放宽` 三处正则。它证明不了两件事：

  - **只在 ≥3 词时附注**：2 词也附注的话，用户会被引导去"改查询"，而短查询的零命中就是"没有"；
  - **真的只发一次请求**：放宽查询必然多打一次 HTTP —— 而"多打一次"在结果集上与"只发一次"**完全同形**，
    只看条数永远看不出来。

  现在跑 SE 与 HN（真夹具）：3 词 ⇒ reason 含 `AND 语义：3 个词` 与 `不自动放宽`；2 词 ⇒ reason 恰好是
  `检索成功但 0 命中`；两臂都断言 `fx.hits.length === 1`。

  ### 后向验证（当场跑）

  | 变异 | 结果 |
  |---|---|
  | `Get-CoverageVerdict`：none/partial 两句换位 | U-120 A 红（`expected 'none' / actual 'partial'`）|
  | SE：`$tc -ge 3` → `-ge 1` | U-175-2 红 |
  | SE：零命中后补一次 `&relaxed=1` 请求 | U-175-1 红（`实际 2 次`，两条 URL 都打出来）|

  第三条是本批的支点：**"没有多做一次请求"这种事，只能数请求**。

## v1.68.0（2026-10-27 结构批 B3-15）：**主流程首次有了行为门** —— U-182 / U-115 改写 + 回放接缝保真。

  这两条契约此前一直只有静态门守着：U-182 的"零产出门槛 ≥3"、U-115 的"缺凭据与失败分列"。
  静态门能证明"代码里写着 3"，证明不了"3 个源时真的告警、2 个时不告警"—— **跑起来才有的东西，只能跑起来验**。

  ### 底座：夹具 → 重建回放语料 → 跑整条 CLI

  `tests/behavior/lib/cli-replay.mjs`（新）：

  1. `recordFromFixture()`：起真夹具跑一遍引擎（就是既有的探针），把**每次请求**与**服务它的那条路由**记下来；
  2. 按 `host + path` 反推原始 URI，与探针带回的 `payload.uris` **逐条对账**（对不上就抛，绝不把键算错降级成"零命中"）；
  3. 写 `responses.jsonl`（键 = `sha256(method\nuri\nbody)` 前 16 位，与产品 `Get-ApiReplayKey` 同构）；
  4. `runCli()`：`MCPS_REPLAY_DIR` 下跑整个 `multi-platform-searcher.ps1`，解析 `-AsJson` 载荷。

  为什么不走产品自带的录制口（`Save-ApiReplayFixture`）：它只在**成功出口**写盘，4xx/5xx 走异常路径录不到 ——
  而这一层最想测的恰恰是失败分档。

  ### 修的第一件东西是接缝自己（U-286）

  第一版 U-115 的 B 臂要求"500 的源进 Degraded"，实跑得到的是 `zero-hit` + `Degraded=[]`。
  不是产品错：`Invoke-ApiReplayOnce` 把录到的 500 原样 `return` 给了 `Invoke-ApiRequest`，
  而后者在 web 路径上默认"非 2xx 早在 cmdlet 里抛了" ⇒ **500 被当 200**，正文被当空 ⇒ 引擎报"检索成功但 0 命中"。

  改法：非 2xx 时**合成一次同形的失败**（PS7 用 `HttpResponseException` + `HttpResponseMessage`，头/正文都带上；
  PS5.1 退化成带状态码的普通异常），于是 `Resolve-ApiHttpFailure` 的重试/`Retry-After`/403 正文留证全部照常。

  ### 第二件：POST 正文不确定（同一个查询换个进程就换字节序）

  重建语料后 CLI 仍 `replay-miss`。查下去：`@{} | ConvertTo-Json` 的**键序逐进程不同**
  （同一份代码两次跑出 `jsonrpc/params/method/id` 与 `params/jsonrpc/id/method`）。回放键取正文哈希 ⇒ 必然 miss，
  而 miss 会被产品 catch 吞成 0 命中 —— 与"源没数据"同形。

  三个 POST 引擎（`grep-app` / `deepseek-search` / `searchcode-repo`）的请求体改成 `[ordered]@{}`。
  副作用是好的：请求可复现，差分调试与缓存都受益。

  ### 改写的两条门

  | 门 | 以前 | 现在 |
  |---|---|---|
  | U-182 | grep `-ge 3` / `Add-EngineWarning`，切片查副作用 | 3 源全零 ⇒ 告警 `3/3`；**2 源 ⇒ 不许告警**；4 源 1 命中 ⇒ `3/4`；跨运行仍查这 3 个源、streak 状态不落盘 |
  | U-115 | grep 四段正则 + 读 2026-09-28 录的旧 JSON | 无令牌 ⇒ `GitHubCode/GitLabBlobs` 进"未请求"；GrepApp 500 ⇒ 进"已请求但失败"且 `failed === Degraded`；**什么都不缺 ⇒ 不许有这一行**；键集不变；控制台两段都在 |

  ### 顺带证伪一条老臂

  `U-282-D GitHub：403 + x-ratelimit-remaining:0 ⇒ rate-limited` 的正文原来写着 `API rate limit exceeded`，
  而引擎的 `$msg -match 'rate-limit|API rate limit exceeded'` 只看文案 ⇒ **响应头丢不丢都能绿**。
  把正文换成 `Forbidden` 之后，唯一的信号才是那个头（与上一条"403 无配额特征 ⇒ forbidden"构成 A/B）。

  ### 后向验证（当场跑，不是"应该会红"）

  | 变异 | 结果 |
  |---|---|
  | 回放接缝：非 2xx 改回 `return`（当成功） | U-286 ① ② 双红 |
  | U-182 门槛 `-ge 3` → `-ge 1` | A-（2 源不许告警）红 |
  | U-182 计数 `$hit -eq 0` → `-ge 0` | B（3/4）红 |
  | `Retry-After` 判据改回只看文案 | U-286 ② 仍绿 —— **说明该臂的真判据是账本行数**（见下） |

  最后一行值得记：`Retry-After` 到底有没有穿过接缝，`rate-limited` 这个码分不出来（丢头也会重试耗尽后报同一个码），

  1. **U-163 函数行数**：`Search-DeepSeek` 因两行注释涨到 102 行（红线 100）。处置是**把理由挪到文件头 + 压成行尾一条**，

  2. **D4 调用图**：负控"删掉 `Test-ApiRetryBudget` 的调用 ⇒ 应报 not reachable"变绿了。

## v1.67.0（2026-10-27 结构批 B3-14）：**证据外置从手工变工具**。

  | 边界 | 为什么 |

  | `-DryRun` 预演 | 批量外置前先看一眼要动哪些 |

  ### 配套的保留策略（U-285-G）

  `reports/provenance/statement-*.json` **只许留最近 3 份**，且当前版本那份必须在。
  没有这条，"更方便的删除命令"并不能阻止证据无限堆积 —— 工具只让清理变便宜，策略才让它发生。
  本批第一次用就外置了 `statement-1.62.0` / `1.63.0`（走工具、进 MANIFEST、不再手抄）。

  ### 两个踩到的实现坑（都写进脚本注释了）

  1. `-File` 调用**不做数组绑定**：`-Path a,b` 是一个字符串 "a,b" ⇒ 脚本自己按逗号拆。
  2. 嵌套 scriptblock 里 `$out += ...` 是**另一个作用域**：累加结果丢在闭包里，调用方拿到空数组
     ⇒ 引用检查静默失效（第一次实跑：被 note.md 引用的文件照样被外置）。改用 `List[string]` 才真的收集到。

## v1.64.0（2026-10-27 结构批 B3-11）：**封套类引擎的状态码分档** —— GitHub / GitLabBlobs。

  B3-3 立的执行器按"结果条数"判（`payload.count`），而这两个引擎返回的是 `contract=engine/1` 的**封套**：
  `payload.count` 恒为 1 —— "1 条结果"与"1 个封套"在那一层**同形**。所以它们一直只在静态契约门
  （u263/u265）里被覆盖，而那些门把传输层桩掉了，桩掉的正是**状态码**。

  这一批拆封套，钉 `failure.reasonCode`（它决定调用方去配令牌、去等配额、还是去查网络）：

  | 臂 | 事实 | 静态门为什么看不见 |
  |---|---|---|
  | 401 + `{"message":"Bad credentials"}` | `missing-credential` | 状态码只在异常消息里；正文没有 "401" |
  | 403 + `x-ratelimit-remaining:0` | `rate-limited`（不是 forbidden） | 要看**响应头**才分得清"配额耗尽"与"没权限" |
  | 403（无配额特征） | `forbidden` | 同上，反向 |
  | 500 | `error` | 重试耗尽后的兜底档 |
  | 200 + `items: []` | `results 0` 且 **failure 为 null** | "搜了没有"是成功；写错就是 L1 把空判成 error |

  ### 又一处同族缺陷（B3-10 修过的那个坑）

  `gitlab-blobs.ps1` 的 401 判据是 `$m = "$_"` + `$m -match '\b401\b|Unauthorized'`。
  **线上 GitLab 的 401 正文恰好写着 "401 Unauthorized"**，所以它"碰巧"判得对 —— 而 `"$_"` 在 PS 7 上取到的是
  **响应正文**（B3-10 在 Sourcegraph 上实测过）。正文一换措辞（`{"message":"Bad credentials"}`，网关改写或上游改文案）
  就退化成 `error`：用户会去查网络，而真原因是没配令牌。
  改法与另外两个引擎一致：`$m = 异常消息 + ' | ' + "$_"`（去重）。**回退即红**（当场验过，`# pass 0 / # fail 1`）。

  ### GitHub 松弛链：证伪一个想当然

  原以为"原查询 0 结果 ⇒ 本地挑一个松弛变体重发"，实测是**每一档都真发**：
  `redis cluster` + `language:Go` ⇒ 3 次请求（原查询 → 去语言 → OR 放宽），最后一次的 `q` 是 `redis OR cluster`。
  这条写成了断言（`fx.hits.length === 3` + 逐个 URL 特征），不是靠读源码相信。
